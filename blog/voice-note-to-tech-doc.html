How to Write a Tech Doc With a Voice Note

Documentation fails because the person writing it already knows how it works. Explaining it out loud to a new teammate surfaces the gaps, and the Tech Doc style turns that explanation into structure you can then correct.

November 19, 2026 7 min read Elaine
Download on the App Store

Key takeaways

  • The reason docs are thin is that the author already knows the answer; saying it out loud exposes the gaps.
  • Record the explanation in three passes: what it is, how to run it, how it fails.
  • Tech Doc gives the structure; the exact commands, versions and paths are still your job.
  • If you cannot follow your own doc on a clean machine, it is not finished.

Every team has a document that says “run the migration script” without saying which directory, which environment, or what to do when it fails halfway. It was written by someone for whom none of that was a question.

Talking through the system out loud moves the author's assumptions into the open: you hear yourself skip the prerequisite, and you notice the step you only know because you did it last week.

How to do it in VoiceNote

Step 1 — Explain it as if a new teammate were listening

Open VoiceNote and tap the mic. Imagine one specific person — a competent engineer who has never seen this system — and explain it to them. Record in three short passes. The free plan takes up to two minutes per note, which suits one pass per note; with Prime a single recording runs to fifteen minutes if you prefer one take.

  • Pass one: what it is. What the component does, what it talks to, and what breaks if it stops.
  • Pass two: how to run it. The order of operations, including the boring preparations you do automatically.
  • Pass three: how it fails. The error messages you have actually seen, what caused them, and what you did. This pass is the one nobody writes, and the one on-call needs.
  • Say what you assume the reader knows. “You'll need access to the staging cluster” sounds obvious to you and is the first thing a newcomer lacks.

Step 2 — Apply Tech Doc

Open each note, tap AI Style Conversion and choose Tech Doc. The style organises the explanation into well-structured technical documentation: sections, steps in order, and a cleaner register than the way you actually talk.

The output is a document draft, not a verified procedure. It inherited your assumptions and it cannot know a command was mistyped or a version moved since you last ran it. Read it with the repository, the terminal and the config open.

Step 3 — Add what speech leaves out

Spoken explanations are strong on intent and weak on exact detail. Fill in these five things before the doc goes anywhere near a newcomer:

  • Exact commands, paths and versions. Copy them from your terminal — do not retype them from memory into a document that someone will trust.
  • Prerequisites. Access, credentials, installed tools, environment variables, and what to do if you do not have them.
  • The check that proves it worked. A specific output, log line or status — not “it should be fine”.
  • The failure section. The three errors most likely to happen, in the reader's words, with what to do about each.
  • Who this is for and when it does not apply. One line at the top saves the wrong reader twenty minutes.

Why talking finds the gaps

Writing documentation is a silent activity, and silence lets you skip anything you already understand. Explaining aloud is sequential: you have to produce the next sentence, and the moment you reach a step you only know instinctively, the sentence stops.

It also changes the audience in your head. Documentation written for “whoever needs it” is written for nobody in particular; documentation spoken to a named colleague includes the parts that colleague would actually ask about.

And it captures failure knowledge while it is still specific. The error you fixed in March is a story you can tell in ninety seconds — and a story is exactly what the doc needs, before it fades into “check the logs”.

A worked example

A made-up example. An engineer explains a rollback procedure, then turns the recording into a runbook.

Spoken explanation, pass three

“Okay, rollback. You only do this if the deploy is worse than what was there before — which is a judgement call, and honestly the thing I got wrong in March. First you check whether the migration has already run, because if it has, rolling back the app does not roll back the schema and you get the crash we had on the seventeenth. So: check the migration table, if today's migration is in there, stop and call me. If it is not, you redeploy the previous tag from CI. It takes about four minutes and the health check goes green twice before the traffic shifts, so do not trust the first green. If the health check never goes green, the previous release is also broken and you are in an incident, not a rollback.”

Tech Doc, with the specifics added

Rolling back a deploy
For on-call engineers. Not the right procedure if a schema migration has already run.

Before you start
Access to the production dashboard and the CI pipeline. Confirm the incident channel is open.

1. Check whether the migration ran
Query the schema_migrations table in the production database. If today's migration is present, stop — rolling back the application will not roll back the schema — and escalate to the platform team.

2. Redeploy the previous image tag
In CI, redeploy the last green tag from the releases pipeline. Typical duration: 4 minutes.

3. Wait for the second health check
Traffic shifts only after two consecutive green checks. One green is not enough.

If it does not recover
A failed health check after rollback means the previous release is also broken: treat it as an incident, not a rollback, and page the platform team.

What changed: the spoken judgement call became a stop condition, the anecdote became a concrete check, and the four minutes is stated so nobody panics at minute three.

Before you publish

  • Follow your own doc on a clean environment. Every step you skip because you know the shortcut is a step the doc is missing.
  • Run every command as written. Copy-paste them from the doc, not from your shell history.
  • Date it and say which versions it covers. Documentation without a date is a rumour.

Mistakes to avoid

  • Documenting what you know instead of what the reader needs. The gap between those is most of the document.
  • Omitting the failure section. Happy-path docs are used once; failure docs are used at 3am.
  • Retyping commands from memory. One wrong flag turns a runbook into a hazard.
  • Writing in your speaking voice. Keep the structure from the style and cut the “so, basically” — the doc should sound calm, not conversational.
  • Leaving no date, owner or scope. Nobody can tell whether the doc is current or authoritative.

Frequently asked questions

Can VoiceNote read my code or repository?

No. It works from your recording, so the accuracy of the doc depends on what you explain and what you add afterwards. Treat the draft as structure, not verification.

How long can one explanation be?

Two minutes per note on the free plan, fifteen with Prime. Long procedures are easier as one note per section — setup, run, verify, fail — than as one long take.

Can I record while doing the task?

Yes, and it is a good way to capture the real order of operations. Stop recording before anything irreversible, and write the commands down afterwards from the terminal rather than from memory.

How is this different from meeting minutes?

Minutes record what a group decided. A tech doc records how a system works or how a procedure is run — the reader is a person who was not in the room.

Should I paste the output straight into our docs site?

Paste it as a draft, then edit it there. The style produces the structure and the wording; the correctness of commands, versions and warnings is your responsibility.

Which languages does VoiceNote support?

VoiceNote transcribes 46 languages. Explain in the language your team reads docs in; style names in the app stay in English.

Once the doc exists, telling the team where it lives is the step that makes anyone read it.
